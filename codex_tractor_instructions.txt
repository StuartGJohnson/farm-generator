The tractor generation code should work as follows: a tractor specification yaml file (see below) will set the sensors, size and layout of the tractor. You will generate python code which will convert that tractor spec file into 1) tractor usda files, 2) isaacsim python code which will use python and python-defined isaacsim action graphs
to bring up the tractor in a defined world (generally provided via our farm generation code), and 3) a tractor urdf file for an actual tractor implementation. Note that, for human testing, it might be handy that the tractor usda can fully define the tractor, but we can discuss this. The end purpose of the tractor generation code is to investigate tractor HW and SW (ros2) design (before an actual tractor is built) to achieve certain goals/metrics in the simulated farm. In
other words, we will be performing a joint partial optimization (or, at least, comparison) over the robot HW and SW design. For example, what do we gain from adding a lidar, or which sensor/SW selection gives us robustness in the presence of high position uncertainty from our GNSS-RTK system. Or, which sensor layout is best.
The tractor generation and simulation code must be repeatable (deterministic) - which is one reason I am not asking you
to generate the end product (the simulation) via generative AI on every tractor specification.

We need to generate usda files for our tractor, and a urdf file for consumption by a ros2 SW stack (e.g., robot_state_publisher). Note this implies we are strict about naming consistency between the urdf and the usda/isaacsim code. The tractor specifications will be defined in a yaml file. We shall intentionally start simple, and verify that our tractor works in isaacsim. The tractor specification is by intention rather generic. You are welcome to embellish the tractor body with a simple mesh/texture if you wish (anything random in your implementation must accept a random seed and be repeatable). Note we are not overly concerned with the appearance of the tractor - although this could effect sensors.


The tractor is composed of a main body and a sensor pod mounted above the tractor. Currently, all sensors are embedded in the sensor pod - with the camera lenses flush with the pod's vertical surfaces. Note that the tractor body is the lower section of
the tractor and volumes may need to be carved out of the tractor body to allow for the tires. When constructing the moment of inertia(s) of the tractor and tires, assume a density of water - there are parts of the tractor that are denser than this, but overall let's assume water density. The placement of the tractor axles within the tractor body should be such that when the tractor suspension has settled - the tractor body should be horizontal (with the given tractor_body_ground_clearance).

For IsaacSim 6.1, we should be using the PhysX 5, Vehicle 2 system, with appropriate settings for tractor tires. Note that we will be defining variable traction via the surface mesh in the world from the farm generation code already present in the repo. For starters, we could just assume appropriate settings for grass or gravel. The tractor vehicle should have some reasonable sort of suspension and ackermann kinematics. All of this should be at your fingertips with PhysX 5, Vehicle 2. The tractor does not currently need a complex, multi-geared transmission. Let's keep this simple, assuming perhaps an electric drive with sufficient torque at all RPMs. Some appropriate suspension from the Physx 5 system should be used, given that the tractor has through-axles and central differentials. For our first implementation, use a 2WD rear drive arrangement.

Code structure/etc:

One could argue that tractor generation should be in a different repo than farm-generation. However,
an integral part of a farming world is combining the farm AND the tractor. Hence, we are in the
current farm-generation repo. I think the best way to do this is put the tractor sw in it's own set
of directories/files. perhaps tractor_generation, etc. In the end, we will have final world bringup script which places the tractor in a given world. perhaps these final bringup scripts should be in a directory called "bringup". One of these will eventually bring up the isaacsim simulation as a ros2 node.
