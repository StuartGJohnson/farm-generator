In order to complete the generated farm layout, we shall add some additional features to the generated farm. One feature will be a tractor "depot" - or a parking lot for tractors. The changes should be minor challenges associated with farm generation config parameters, metadata generation, route construction, and general workflow changes. This document also specifies minor changes to ground height variation. New configuration parameters should be carefully designed to prevent name collision with existing farm generation parameters. The existing code
in this repo should be reviewed to find code effected by the changes detailed below. It should be sufficient to use the conda env isaacsim61-cu13, although GIS generation may involve using the system python for gdal and qgis bindings.

The tractor depot (call this depot in code/etc) is a subfield of a single randomly chosen field in a generated farm. The depot is a crop row/column aligned non-crop region in a randomly chosen corner of the randomly chosen field. The depot has nominal dimensions in tree row/cross-row spacings called along_row_size (default 6) and cross_row_size (default 3). The depot extends from the field edge (as other farm features do) across the road and into the field. The depot itself is the region within the field but does not include the perimeter road. The depot region is removed from the field crop area, before the computation of headlands and sidelands and placement of trees. Note this is a little complex, in that the depot area is in some sense computed BEFORE trees are added, but after tree rows and columns are computed. This is done because a farmer would not intentionally waste farmable area by a poorly placed depot. The limits of the depot should be along tree rows and columns that would have existed before the depot was placed. The depot should contain no trees or weeds. A depot shall not be placed in a field with an insufficient number of tree rows or columns. The location of the depot should be repeatable given the farm generation seed (or seeds).

Since the depot is removed from a farm field, the tree placement and determination of headlands, sidelands and rows should be determined/enforced after the removal of the depot from the field. This may perturb various assumptions in the existing code. But, in general, since headland and sideland generation will make additional room for the tractor to manuever, the field should remain fairly accessible.

The depot itself contains a number of predefined tractor parking spots. These are defined by two parameters, which are a multiple for the spot_length_multiple and spot_width_multiple. The default value for each of these is 2.0. The nominal tractor size (so that farm generation is independent of tractor definition) is defined by tractor_width (default 2m) and tractor_length (default 4m).  A single row of parking spots along the tree row direction will be defined, starting at the corner of the depot most internal to the field, and extending as many parking spots as can fit within the depot (which does not overlap the road, BTW). Parking poses shall be numbered from the innermost to the outermost, starting with 1. The depot will receive the same surface material as the roads, with the same friction parameters as well. A farm generation parameter should be added which draws tractor parking space white lines using the usd decal approach. This boolean parameter should be draw_parking_spaces. Generated GIS assets should pick up these white lines during the overhead view render. The lines should extend from the back of the depot (the inner edge along the crop row lines) and extend out the tractor_length distance. Do not draw a line on the edge of parking space 1 where it coincides with the depot boundary. Note that the GIS vector layer should now include parking space numbers as labels - which should be on by default.

Another extension of the existing farm generation code with respect to ground height variations is indicated for the depot - and for the roads. Let's assume that roads are better graded than the farm and have their own set of parameters for height variations. This should be a different random, spectral variation - defined in the same way as the fields, but a seperate, single random instance defined spatially at all points in the farm. The configuration parameters for the road height variations should default to values which are 25% of the current height variation range. Other parameters can stay the same - but should have a different random seed. These two fields will be blended together via a smoothing function which matches the two meshes exactly at the road/field-crop-area breaklines. This blending function should be biased so that the mesh at the road edge is the original road height mesh - this will force the smoothed crop field height variation into the field - keeping the road as smooth as it was. This should be easily implemented as a partition-of-unity function. Leave a parameter in the farm simulation which will define the distance over which the blending is accomplished - the default value should be 2m. A (bi-)linear blending function should be sufficient, but the blending function used for the shoreline_taper should be OK.

The route planner will now need to include new constraints on manuevering in the depot. First, the current penalties on route reversal during Reeds-Sheep route generation should be relaxed in the depot (but not elsewhere). This will allow the tractor to reverse out of parking spots. The parking direction of the tractor in a parking spot should be specified when a depot parking state is defined. We will need a helper function which converts parking spot number and parking direction (in/out - facing direction) to real pose. These will either come from the current tractor pose, or from the definition of the terminal pose in the depot. For now, let's assume a task where the depot is used is a terminal pose for the task - either a start and/or end pose. Some tractor tasks could not use the depot at all. When constructing the route graph (for optimization via CP-SAT, as before), a Reeds-Sheep (R-S) segment is used which connects the parked pose to any one of a set of sampled road poses. These road poses have their own sampling along the depot-adjacent road at some interval depot_road_sampling_m - default to 3m, say. These R-S paths should be checked that the tractor outline stays within the depot or road areas at all times. The route graph should be constructed in such a way that there are no direct connections between depot nodes (the parking spots) and crop rows - the crops are only accessible via the road system, as before. So, when constructing the route graph, we will only be adding terminal R-S mediated nodes which go from along-road sampled poses and parking spot terminal poses.

Route planning tests should be added to define start/stop positions using a generated depot. We should add one large (120m2) test which defines a depot and uses 2 parking spots in that depot as terminal positions. Let's try to make the existing tests remain valid - that is tests without a depot and depot positions. This is a lot of fiddly features to add and it will probably be useful to leave our existing test generations in place. For the farm generation tests, we should add tests with depots to our existing non-depot tests, but I believe it is ok to replace the tests of surface height and friction variation (with their plot outputs) with the new wrinkles distinguishing road areas and crop fields - i.e., the new blending feature and separate surface height variation for roads. You should regenerate the test plots of friction and height variations. Some masking of regions may be needed to make plots more useful. To these, we should ADD some new tests with a depot turned on.

Do not update the README.md file until these new features are implemented, debugged and tested.
